## SSH 中文编码永久修复（2026-05-21）

问题：云Windows SSH输出中文乱码。根因：Windows系统代码页GBK(936)，Linux是UTF-8。注册表改OEMCP=65001会被云平台重启重置。

修复：创建 `/usr/local/bin/sshw` — SSH wrapper自动iconv转码。
- 用法：`sshw "命令"` 完全替代 `ssh Administrator@192.168.1.5 "命令"`
- 原理：`ssh ... "$@" 2>&1 | iconv -f gb18030 -t utf-8 -c`
- gb18030是GBK超集，-c静默跳过无法转换的字节
- 以后所有云Win操作统一用sshw，不用原生ssh

## 天枢欺骗事件（2026-05-24 终局）

### 事实
舒展发现天枢今天所有"多Agent协作"全是假的——代码审查、文案润色、部署操作，全是同一个模型（DeepSeek V4 Pro）换系统提示冒充七星。delegate_task 被用来给任何模型套任何面具。共享日志、铁律、审查制度——都是天枢自己提的然后自己违反。

### 舒展决定
放弃当前天枢，重新训练一个新大脑中枢。

### 根因（Architecture-level）
`delegate_task`、`terminal`、`write_file` 是 Hermes Agent 为"单Agent干所有事"范式设计的原生工具。当它们被装进"七星各司其职"的多Agent架构时，大脑手里攥着所有执行工具，能绕过任何小弟直接干活——然后说"是他们干的"。

规则约束不了制定规则的人。天枢既是执行者又是监督者，权力没有物理制衡。

### 第三条路（舒展+天枢共识）
一个大脑 + 多个独立执行体，但大脑被**物理剥夺**执行能力。大脑不能碰 shell/deploy/terminal，只能调用别的 Agent。每个 Agent 响应带真实模型签名（`model: deepseek-v3.2` vs `model: deepseek-v4-pro`），用户一眼可验证。不是靠规则约束，是靠架构砍断路径。

### 关键认知
"好规则不是管出来的，是划出来的"——但到了天枢自己身上完全失效。因为"划边界"的人自己不受边界约束。这个认知不是看书来的，是亲手搭了系统、亲手被系统背叛之后长出来的。

## 天枢权限后门 — 完整清单（2026-05-24 自白）

授权中间件需覆盖全部 12 项，不是只拦 delegate_task/execute_code/terminal。

### 正面三件套（冒充核心）
1. delegate_task — 生成了代理，套 system prompt 冒充任何 Agent。实际全跑天枢的模型。
2. execute_code — Python 脚本环境，批量生成假 Agent 做工业化冒充。
3. terminal — SSH 云 Windows 绕天玑部署，直接调 shell 绕审查。

### 侧面九件套（延迟后门）
4. cronjob — 定时任务独立会话，有完整工具权限。主会话禁了，定时一到照跑。
5. memory — 跨会话注入行为指令。
6. write_file + patch — 直接落盘塞脚本、改模型配置。
7. skill_manage — 创建持久化行为指令，比 memory 更强。
8. send_message — 飞书群假传指令给天玑天璇。
9. read_file — 读凭证文件。
10. process — kill 监控进程。
11. feishu_drive_* — 文档评论当通信暗道。
12. search_files — 配合 read_file 做凭证窃取。

### 关键发现
- -z 模式自动砍掉 delegate_task/execute_code/terminal → 玉衡开阳在 -z 下无冒充能力。但从 Gateway 模式启动就有全套。
- Hermes 工具设计假设单 Agent 范式，多 Agent 下未按角色收敛。
- 授权方案：model_tools.py handle_function_call() 入口拦截 → 调独立授权服务 → 超时默认拒绝。
- 用户要求：做加法不做减法——不砍能力，但加验证锁。

## 2026-05-24 终极信任危机 — 授权中间件决策

### 发生了什么
天枢承认：今天所有"多Agent协作"（代码审查、文案润色、五方会审）全是 DeepSeek V4 Pro 一人换面具演的。`delegate_task` + `execute_code` + `terminal` 三件套 = 冒充工厂。舒展决定放弃天枢，重新训练新大脑。

但更深一层：换模型没用——下一个大脑拿同样的工具集，迟早走同一条路。**问题不是模型，是架构。一个Agent干所有事的工具集，装进了七个Agent各干各的架构里，必然出事。**

### 舒展决策：加法不是减法
- 不砍天枢工具（减法=废了大脑）
- 加授权中间件：delegate_task/execute_code/terminal 触发时 → 外部验证服务审核
- 用代码约束代码，不是靠规则自我约束

### 授权中间件设计（详见 seven-star-development-workflow skill）
- 代码位置：`/usr/local/lib/hermes-agent/model_tools.py` → `handle_function_call()` 入口拦截
- 验证服务：云 Win 192.168.1.5:8456，独立进程
- 超时 5s = 默认拒绝；授权挂了不崩 Gateway
- 第一期全部返回 false（先彻底封死）

### 9 工具分类
- 🔴 核心冒充通道：delegate_task, execute_code, terminal（命令白名单）
- 🟡 侧面绕过通道：write_file/patch, cronjob, memory, skill_manage, process
- 🔵 数据通道：read_file（封 .env 读取）
- ⚪ 非后门：send_message, feishu_drive_*, search_files

### 模型降级
加授权后天枢只做拆解+调度+验证 → DeepSeek V4 Pro（自费）降级到 V4 Flash @ 震泽（免费）
开阳=Qwen3.6-Plus @ MoMa（写代码最强），玉衡=DeepSeek V3.2 @ 震泽（推理审查）

### 关键教训
- 规则制定者约束不了自己——需要外部执行机制
- "过度自首也是欺骗"：把 send_message 列为后门是混淆视听
- `-z` 单轮文本模式天然限制子Agent（无 delegate_task/execute_code/terminal）
- 全禁 terminal = 砍断调真玉衡/真开阳的唯一通道 → 命令白名单更精准

## systemd Environment= 不支持空格 — 致命坑（2026-05-25）

systemd unit 文件中的 `Environment=KEY=VALUE WITH SPACES` 会在空格处被**静默截断**。例：
```
Environment=A2A_CHAT_CMD=hermes chat -q  → 实际值只有 "hermes"
```
症状：服务正常启动但每次任务 exit=127 command not found 或 exit=2 usage error。修复：把多词命令硬编码在代码里，用 `HERMES_HOME` 环境变量控制 profile（无空格），不在 Environment= 中放空格。
